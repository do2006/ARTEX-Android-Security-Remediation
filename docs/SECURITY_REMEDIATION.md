# Security remediation status

This branch hardens the Android wrapper. `assets/backend/artex` was rebuilt from the pinned upstream ARTEX source on 2026-11-23, but the backend's TLS, authentication, authorization, archive handling, and command-execution behavior have not been security-reviewed or runtime-certified.

## Safe defaults now enforced

- Tool and skill catalogs are pinned to reviewed immutable commit `c1fa82a2507be24c2f3f219137f74b7832812e7d`. Entries require a strict basename, valid SHA-256, the exact `Srysfu/artex-mobile-tools` GitHub release route, HTTPS port 443, and at most three redirects to approved GitHub release delivery hosts before download or installation.
- Catalog-installed binaries are statically checked but are not executed as an install probe.
- The pinned native-tool catalog and Python wheelhouse contain AArch64 Android payloads. The app checks for an `arm64-v8a` ABI before downloading tools or installing Python packages. x86_64 translation is experimental and not release-certified: the available emulator installs the wheels, but known native extension failures prevent full tool validation.
- The backend binds only to `127.0.0.1`; LAN sharing is disabled by default.
- Unlocked network `pip install` is disabled. The APK contains a 96-wheel Android arm64/Python 3.14 wheelhouse and committed hash lock. Installation is an explicit panel action, offline, and checks the lock SHA-256 plus pip `--require-hashes`; packages install into a staging directory and replace the prior install only after entry-point checks pass. The backend is restarted after install so its `PYTHONPATH` and `PATH` include the package.
- A Firebase Test Lab Robo run of the current test-signed APK on a Medium Phone ARM virtual device with Android 14 (API 34) passed (1/1 device). The run lasted 5m 9s; Robo exploration timed out at 4m 59s after 82 actions, 4 activities, and 19 screens. This provides ARM virtual-device install and automated exploration evidence, but it does not verify the app's explicit Python-tools installer or any tool command. The APK was signed with a temporary test certificate, not the release key.
- A standalone x86_64 emulator test ran translated CPython 3.14.10 with no `LD_LIBRARY_PATH` and imported `ssl`, `bz2`, `lzma`, `sqlite3`, and `zlib`; a scratch `--require-hashes` install of the 96 ARM64 wheels passed. `impacket`, `pypykatz`, and `lazagne` imports passed, and `laZagne --help` exited successfully. `nxc --help` failed in `netifaces` with unresolved `PyExc_OSError`; `pypykatz --help` failed to load the OpenSSL legacy provider; lxml and Pillow native extensions also failed with unresolved Python symbols. These scratch checks used `/data/local/tmp`, not the app install flow. Static ELF inspection also finds unresolved optional Pillow AVIF/font libraries.
- The five core binaries are downloaded during initial setup; other catalog entries remain user-selected downloads in the Tools panel. Catalog entries are hash checked, but this does not amount to runtime validation of every tool or every feature.
- Android Auto Backup is disabled. Cleartext is denied by default and allowed only for `http://127.0.0.1:8787`; WebView main-frame navigation is limited to that local service and file access is disabled.
- New backups use a version-2 `manifest.json` written before archive contents. Restore parses it, rejects malformed/empty or legacy manifests, enforces ZIP path and expansion limits, and verifies SHA-256 for every declared file before accepting the restore.
- Restore reports a failed rollback instead of silently discarding it. PostgreSQL shutdown retains the process reference until it has actually exited.
- Release signing passes password source names (`env:ARTEX_KS_PASS` and `env:ARTEX_KEY_PASS`) to `apksigner`; passwords are no longer placed in its command-line arguments.

## Follow-up required

- Complete signed provenance for the rebuilt backend and reproducible, signed provenance for PostgreSQL assets before enabling LAN access, TLS, or server-side authentication changes.
- Backups remain in internal app-private storage and are not encrypted or signed. The v2 manifest detects accidental tampering/corruption but is not a trust signature. Implement authenticated encryption with a user-selected passphrase and recovery UX before adding any export flow.
- Legacy backups with the prior unverified manifest format are intentionally rejected; users must retain the source device and create a fresh v2 backup before migration.
- Pin and verify all build inputs, including Termux packages and the Android signing environment. `env:` keeps signing passwords out of process arguments, but environment-based secrets still require a controlled build host and must never be logged.
- Complete the Android native-library closure, then test Python-tool installation, all four command entry points, and representative features on a native ARM64 device or genuine ARM virtual device before publishing. The passing Robo run verifies app installation and automated screen exploration only. A source package name, cross-pip install, successful APK build, or Robo pass alone does not prove tool functionality. Android sandbox restrictions remain: LaZagne cannot read other apps' private credential stores or a desktop Secret Service; pypykatz can parse user-provided LSASS dumps but cannot access Windows LSASS from Android; individual NetExec/Impacket protocols may require unavailable Android facilities or native libraries.
